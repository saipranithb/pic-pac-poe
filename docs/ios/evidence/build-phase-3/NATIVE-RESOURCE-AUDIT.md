# Native resource and minimum-platform audit

The independent source audit found a missing native app icon: Build Phase 2 contained no asset catalog, app-icon build setting or compiled icon metadata. A successful unsigned simulator compile did not establish archive resource completeness. Phase 3 corrects this ordinary product defect without signing or store work.

`ios/PicPacPoe/Assets.xcassets/AppIcon.appiconset/AppIcon.png` is an opaque 1024×1024 sRGB image rendered directly from the unchanged canonical Android `ic_launcher_background.xml` and `ic_launcher_foreground.xml` paths. It preserves the 108×108 coordinate system, cocoa diagonal band and grid, coral X, pistachio O, original symbol proportions and overlap. It does not copy an Android adaptive mask or screenshot; iOS applies its native icon shape. The full-resolution PNG was visually inspected, and two renderer executions produced byte-identical output. No new branding or external artwork was introduced.

The reproducible renderer is `ios/Scripts/GenerateNativeAppIcon.swift`. It supports only the commands in the current canonical vectors and fails on an unsupported command instead of silently approximating source changes. Exact source, output, renderer and license hashes are in `native-asset-provenance.json`. The source artwork and adaptation use the repository's Apache-2.0 license, Copyright 2026 Pic-Pac-Poe contributors; the original project `LICENSE` remains authoritative. The existing Fredoka files and SIL OFL license are unchanged.

A semantic `LaunchBackground` named color now supplies cream `#FBF1DE` for light system appearance and cocoa `#251F1C` for dark system appearance through `UILaunchScreen.UIColorName`. This avoids the platform's unstyled launch background while restoration loads. Native launch screens follow system appearance; a separately saved in-app theme is applied after local settings restore. The launch screen is a static background, does not reconstruct a match, and adds no decorative or game state.

The catalog is included in the ordinary application Resources phase and `ASSETCATALOG_COMPILER_APPICON_NAME` selects `AppIcon`. The Release verifier now checks compiled icon metadata for iPhone and iPad, the catalog, launch color reference, exact bundled Fredoka/OFL and Q-policy bytes, absent test fixtures/signing material, bundle/version identity, iOS 17 minimum, and exclusion of development launch hooks and LLVM coverage/profile instrumentation. The shared CI-contract gate checks resource provenance hashes without refreshing them.

Source inspection retains iOS 17 compatibility: Observation, the two-argument/initial `onChange` form and SwiftUI accessibility APIs used by the app are available at the declared minimum or earlier. A successful build with deployment target 17.0 confirms compile-time API availability only; it cannot prove runtime behavior on iOS 17. The local host has only iOS Simulator 26.5, as recorded by `ci-logs/installed-runtimes.json`. No runtime installation or global developer-directory change occurred.

Earlier unsigned Release builds for both generic iOS Simulator and generic iOS device SDK passed identity/resource verification on `ad1a3b40570406a7cf967c600a7c88516dbf2c0c`, as did unsigned Debug device SDK compilation. Independent inspection then found LLVM coverage instrumentation, so those binaries are superseded. Final Debug and Release builds for both simulator and device SDKs now pass on `03d44f794ef98e66ebeb63cd467313ece2331b91`; the [final build manifest](unsigned-builds-final-20260925/manifest.json) retains exact source, commands, full app-file hashes and actual Mach-O output. Both final Release binaries contain zero LLVM coverage/profile sections, and their compiler commands contain no instrumentation flags. The [coverage finding](defects/release-coverage/finding.json) retains their exact source and binary hashes. Their native icon metadata for iPhone/iPad and launch dictionary containing only `UIColorName: LaunchBackground` were valid. Every Release Mach-O slice declares minimum iOS 17.0 and its correct simulator/device platform; neither Release executable contains development launch hooks, and neither app contains signing material. These are actual compiler/resource checks, not iOS 17 or physical-device runtime validation. Physical VoiceOver/Switch Control/keyboard focus and real launch/device appearance remain device-validation evidence requirements; source modifiers alone are not human certification.
